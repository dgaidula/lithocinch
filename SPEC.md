# lithocinch → Craft CMS plugin: architecture spec

Design doc for the CMS-facing product built on top of the `lithocinch` core.
Captures decisions, the service backbone (already built), and the Craft plugin
(to build). Keep this current as decisions land.

Status legend: **[done]** in this repo · **[todo]** to build (likely a separate
plugin repo) · **[decision]** settled choice.

---

## 1. The shape of the whole thing

```
Craft template / upload  ──▶  Craft plugin (PHP)
                                 │  reads source bytes via Craft Fs (GCS/S3/local)
                                 ▼
                          backend driver  ──▶  lithocinch core (Node/sharp)
                            cli | daemon | remote        resize + perceptual + auto-format
                                 ▲
                                 │  optimized bytes back; plugin writes via Craft Fs
                          transform filesystem (GCS) + index/manifest
```

**[decision] Bytes in, bytes out — the Node service is stateless and
storage-agnostic.** The Craft plugin owns all storage through Craft's `Fs`
abstraction, so GCS/S3/local need *zero* service integration. Verified target:
`craftcms/google-cloud` on Craft 5.10 (CAF + TLB).

## 2. Service backbone — **[done]** in this repo

One request/response contract, three transports, one `runTransform()` core
(`src/transform-api.js`):

| Transport | Entry | Driver it powers |
|---|---|---|
| CLI (stdin→stdout JSON) | `lithocinch transform` (`src/cli-service.js`) | `cli` |
| HTTP daemon | `lithocinch serve` (`src/server.js`) | `daemon` |
| AWS Lambda | `lambda/transform.js` (Function URL / API GW v2) | `remote` |

Contract (image as base64; `batch` = one source → many outputs for `<picture>`):

```jsonc
// request
{ "image":"<b64>",
  "ops":{ "width":800,"height":600,"fit":"cover","focal":{"x":0.3,"y":0.6},
          "maxSize":2560,"bg":"#fff" },
  "format":"auto",                                  // jpeg|png|webp|avif|keep|auto
  "batch":[ {"ops":{"width":800},"format":"avif"},
            {"ops":{"width":800},"format":"webp"},
            {"ops":{"width":800},"format":"auto"} ],
  "defaults":{ "perceptualTarget":0.99, "formatPool":["avif","webp","jpeg"] } }

// response
{ "ok":true, "outputs":[
  {"format":"avif","width":800,"height":533,"bytes":1914,"ssim":0.997,
   "engine":"avif-lossy","data":"<b64>"} ] }
```

`fit` ↔ Craft modes: `cover`=crop, `inside`/`contain`=fit, `fill`=stretch.
`focal` = focal-point cover crop (static images). Auth: optional bearer
`PI_TOKEN`. Batch amortizes Node startup / network.

## 3. The two optimization layers (and the Twig/on-upload answer)

There are **two independent layers**; the plugin should offer both and explain
the difference, because they serve different goals.

### A. On-upload source optimization (storage / GCS savings) — **[todo]**
Hook `Assets`/`Elements` save events (the Verbb Image Resizer model) to **cap +
perceptually optimize the stored original** on upload.

- **[decision] Keep the source format on upload** (cap size + same-format
  perceptual compress). Do NOT convert the source's format/extension — that would
  break references, downloads, and integrations. Format conversion belongs at the
  delivery layer (transforms).
- Goal served: **smaller originals in GCS** (designers upload 6000–8000px files;
  capping to ~2560–3840 + perceptual compress is a large reduction), and faster
  transforms (less to read/decode).
- One-way door: the pristine original is replaced. Mitigate by setting the cap
  generously and offering an "optimize but keep a cold backup" toggle.
- Preserves focal points (relative 0–1; survives proportional resize — we cap,
  never crop, on upload).

### B. Transform-time delivery optimization (pagespeed) — **[todo]**
A custom `ImageTransformer` (Craft 4.4+/5) so template transform requests are
generated by sharp + auto-format, cached as derivative files.

**What happens in Twig if the source was already optimized on upload?** The two
layers compose; nothing conflicts:

1. **Templates that already call `asset.getUrl({width: 800})`** → register the
   plugin as the **default transformer** and those *existing* calls now emit
   AVIF/WebP, right-sized, cached — **with zero template changes.** This is the
   drop-in pagespeed win. The pre-optimized source is just a cleaner/smaller
   input to the transform.
2. **New responsive markup** → `craft.imageOptimize.picture(asset, {...})` emits
   the `<picture>`/`srcset` set (avif/webp/fallback × widths) via batch requests.
3. **Templates that use the raw `asset.url`** (no transform) → serve the
   on-upload-optimized source directly: smaller and cleaner, but single-size /
   single-format (no responsive, no `<picture>`). Partial win.

Net for CAF/TLB: **smaller sources in GCS (layer A) + small cached delivery
variants + faster pages / better PageSpeed (layer B).** Caveat: transform
variants also live in GCS (the transform Fs) and are purgeable; they're tiny
(right-sized, modern format), so the source cap usually dominates net storage.

> The headline: with the transformer registered as default, **sites that already
> use Craft transforms get the AVIF/WebP + perceptual win automatically.** On-
> upload is the separate lever for GCS source savings.

## 4. Craft plugin integration surfaces — **[todo]**

1. **Custom `ImageTransformer`** (`ImageTransformerInterface` +
   `EagerImageTransformerInterface`, Craft 4.4+/5). Core of the delivery layer.
   `getTransformUrl()` → cache-key lookup → backend driver → store variant in the
   transform Fs → return URL. Cache key = assetId + transform params + source
   hash/mtime + transformer version + focal point. Verify exact interface across
   Craft 4.5.x and 5.x (it shifted slightly).
2. **Twig API** via a `CraftVariable` behavior:
   - `craft.imageOptimize.url(asset, {width, format:'auto', ...})` → single best `<img>` src.
   - `craft.imageOptimize.picture(asset, {widths, formats, sizes})` → full `<picture>`.
   - `craft.imageOptimize.srcset(asset, {...})` → srcset string.
3. **On-upload optimization** (layer A) — event handler, toggleable, separate.
4. **Bulk utility + queue job** — CP Utility + element-index action to (re)optimize
   existing assets / regenerate variants; surfaces total-bytes-saved stats.

## 5. Backend driver model — **[done in service; plugin glue todo]**

| Driver | Needs | Use | Edition |
|---|---|---|---|
| `cli` | Node + tool on server (Symfony Process) | most Craft VPS/managed | Lite |
| `daemon` | Node + kept-alive `serve` process | high-volume self-host | Lite/Pro |
| `remote` | HTTP + API key (the Lambda) | any host, incl. no-Node | Pro / hosted |

## 6. Caching, storage, invalidation — **[todo]**
- Variants stored in a configurable transform **filesystem** (GCS via
  `craftcms/google-cloud`, or a separate bucket/CDN).
- A transform **index** (own table or Craft's) maps cache-key → stored variant +
  chosen format (auto-format means the extension isn't predictable — same role as
  the core's `--manifest`).
- Invalidate on `asset.dateModified`, focal-point change, transform-definition
  change, or transformer-version bump. CP action to purge.

## 7. Async strategy — **[decision] queue-eager default**
On asset save / first transform reference, enqueue a `BaseJob` to pre-generate
variants; serve the original (or a placeholder) until ready. Offer lazy
synchronous generation with a timeout → original fallback. The AVIF shootout is
too slow to reliably block a cold first request.

## 8. Settings / config / editions — **[todo]**
- Project-config-aware settings: `driver`, `nodePath`/`toolPath` (cli),
  `serviceUrl` (daemon), `apiUrl`+`apiKey` (remote, key in `.env`),
  `perceptualTarget`, `maxSize`, `formatPool`, default `formats`, transform Fs
  handle, eager-vs-lazy, on-upload toggle + cap.
- `config/image-optimize.php` overrides (Craft convention).
- **[decision] Editions:** Lite (resize + WebP, local driver) vs Pro (auto-format
  + AVIF + the transformer + `picture()` + remote/hosted). Plugin Store licensing.

## 9. Cross-cutting decisions — **[decision]**
- **Craft 4 + 5 both** (user manages both). Watch the transformer-interface delta.
- **bytes-in/bytes-out** service; storage via Craft Fs (GCS verified).
- **JPEG competes only if it clears the perceptual bar** (`auto` pruning).
- **Tie-break = most compatible** within `--format-tolerance`.
- **AVIF in the default pool**; `<picture>` provides the fallback for the gap.
- On-upload keeps source format; transforms do format conversion.

## 10. Open decisions
- Transformer depth for v1: full native `ImageTransformer` (best feel, more work)
  vs Twig-only writing its own cached files (faster ship). Leaning native.
- `remote` payload: base64 JSON (simple; current) vs raw-body variant (−33%
  overhead) when payloads grow.
- Hosted billing model + tiers (separate SaaS concern).
